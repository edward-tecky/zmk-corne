### ZMK-SEC-001 — Mutable keymap drawer code receives repository write permission

**Severity:** High
**Class:** Supply-chain risk
**Evidence:** `.github/workflows/draw.yml:12-17`; Task 1 workflow inventory `security/audit/workflow-inventory.tsv:8` records requested `main` resolved to `3a4ca7e060a54ba700d3e7b6a43cb0b9cec347d2`.
**Impact:** Compromise or retargeting of `caksoylar/keymap-drawer` can execute attacker-controlled workflow code with permission to commit to this repository.
**Scenario:** Trusted `push` or manual dispatch starts Draw Keymap; caller resolves `@main`; called workflow receives `contents: write` and `destination: "commit"`; malicious replacement code pushes an arbitrary repository change.
**Recommendation:** Pin called workflow to reviewed commit `3a4ca7e060a54ba700d3e7b6a43cb0b9cec347d2`; preserve `contents: write` only in separate tightly scoped generation job if automatic commits remain required, otherwise generate artifact or pull request without write token.
**Regression risk:** Immutable pin stops automatic upstream changes; removing write permission changes generated-keymap publication flow.
**Verification:** Dispatch workflow from pinned commit; confirm only intended `keymap-drawer/**` change commits; inspect job token permissions and deny arbitrary repository write attempts.

### ZMK-SEC-004 — Unsecured module RPCs bypass Studio lock for bond and activity mutations

**Severity:** High
**Class:** Authorization / management integrity
**Evidence:** BLE management registers `cormoran_ble` as `ZMK_STUDIO_RPC_HANDLER_UNSECURED` at audited clone `/tmp/zmk-corne-security-audit/zmk-module-ble-management/src/studio/ble_management_handler.c:50-66` and exposes profile switching/unpairing, all-bond deletion, and output selection at `/tmp/zmk-corne-security-audit/zmk-module-ble-management/src/studio/ble_management_handler.c:379-447` and `/tmp/zmk-corne-security-audit/zmk-module-ble-management/src/studio/ble_management_handler.c:491-550`, all at `851661cd21f2aded8ec649da86e01a207dc4b973`. Settings RPC registers `zmk__settings` unsecured at `/tmp/zmk-corne-security-audit/zmk-module-settings-rpc/src/studio/settings_rpc_handler.c:20-40` and mutates idle/sleep settings at `/tmp/zmk-corne-security-audit/zmk-module-settings-rpc/src/studio/settings_rpc_handler.c:207-253`, all at `78f86df9e6c5edaf57bef3ccbd7f360cfdf49291`. Fork dispatch checks the Studio lock only for subsystems marked `SECURED` at `/tmp/zmk-corne-security-audit/zmk/app/src/studio/custom_subsystem.c:90-113` at `4493783ef88ce2e653bf8217c92ee17140df71e3`. Both handlers are enabled in `boards/shields/eyelash_corne/eyelash_corne_left.conf:14-25`; settings changes relay to the enabled right-half event receiver.
**Impact:** A host allowed to reach Studio custom RPC can mutate keyboard connectivity and persistent central activity policy without physical `&studio_unlock`: it can switch or remove host profiles, call `zmk_ble_clear_all_bonds()` through the nominal split-bond method, select output transport, or request activity-timeout relay to the peripheral. BLE Studio still requires its transport's encrypted GATT permissions (`/tmp/zmk-corne-security-audit/zmk/app/src/studio/gatt_rpc_transport.c:88-94` at `4493783ef88ce2e653bf8217c92ee17140df71e3`); USB requires physical host access. This finding does not claim unauthenticated radio reachability.
**Scenario:** Encrypted BLE Studio client or attached USB host lists custom subsystems, calls unsecured `cormoran_ble.forget_split_bond`, and reaches `zmk_ble_clear_all_bonds()`; alternatively it calls unsecured `zmk__settings.set_activity_settings`, whose central setters schedule persistence and attempt a fixed `as` relay event. Central success does not prove delivery or peripheral application: the handler ignores the event-raise result and returns from central setter status alone (`/tmp/zmk-corne-security-audit/zmk-module-settings-rpc/src/studio/settings_rpc_handler.c:211-252`), while the peripheral listener ignores both setter results (`/tmp/zmk-corne-security-audit/zmk-module-settings-rpc/src/events/activity_settings_changed.c:19-37`), all at `78f86df9e6c5edaf57bef3ccbd7f360cfdf49291`. Enabling Studio locking later would not block either subsystem because their metadata remains `UNSECURED`.
**Recommendation:** Mark every state-mutating BLE/settings method `SECURED`; if read-only profile/status methods must remain available while locked, split read and mutation operations into separately classified subsystems or add explicit per-method authorization before mutation. Rename or narrow `forget_split_bond` so its implementation cannot erase unrelated host bonds. Validate activity timeout policy before central mutation and split propagation.
**Regression risk:** Clients that currently manage bonds or activity while locked will require physical unlock; separating read/write methods changes subsystem identifiers or client routing. Narrowing bond deletion can change reset/re-pair recovery flow.
**Verification:** With locking enabled, test every method over USB and encrypted BLE before and after physical unlock. Before unlock, assert all mutation methods return `UNLOCK_REQUIRED` and cause no bond, transport, timeout, settings, or split event change; decide and test read-only policy separately. After unlock, verify intended per-profile and split-only bond deletion using disposable identities, then confirm idle/sleep values on both halves. Hardware tests are required; none were run in this audit.

### ZMK-SEC-005 — Device-provided `javascript:` UI URLs execute in the Studio origin

**Severity:** High
**Class:** Vulnerability / untrusted URL navigation
**Evidence:** Custom subsystem metadata is received from the connected device and includes arbitrary `uiUrl` strings (`/tmp/zmk-corne-security-audit/zmk-studio-ts-client/src/custom.ts:15-25` at `39083858775d320018716e3d8fd68d00f6d11118`). DYA has an `http:`/`https:` validator, but applies it only when reloading previously trusted URLs from storage (`/tmp/zmk-corne-security-audit/dya-studio/src/pages/CustomSubsystemsPage.tsx:69-94`). A new device-provided URL is placed directly into the warning flow and, after confirmation, passed to navigation without validation (`/tmp/zmk-corne-security-audit/dya-studio/src/pages/CustomSubsystemsPage.tsx:362-383`); navigation is `window.location.assign(url)` (`/tmp/zmk-corne-security-audit/dya-studio/src/lib/navigate.ts:1-7`). The dialog does show the exact URL, warns that the firmware author supplied it, and requires an explicit Open click (`/tmp/zmk-corne-security-audit/dya-studio/src/pages/CustomSubsystemsPage.tsx:158-200`), so exploitation is not drive-by. Audited source SHA: `2c31a8655dcef95589ce6131a0797ccc19c618b8`.
**Impact:** A hostile or compromised keyboard firmware can advertise a `javascript:` URL. If the user selects it and confirms the warning, script executes in `studio.dya.cormoran.works` rather than an external origin. It can read same-origin settings/keymap caches and trusted-URL state and act with the user gesture; browser policy and existing device grants determine whether additional Web Serial, WebUSB, Bluetooth, or clipboard operations succeed. The client disconnects immediately before navigation, reducing live-session exposure but not same-origin or retained-permission exposure.
**Scenario:** User connects an untrusted keyboard, opens its unsupported-subsystem link, sees `javascript:...` in the warning, and clicks Open. `location.assign` evaluates the firmware-controlled script in the Studio origin.
**Recommendation:** Parse and allowlist each fresh URL before display, storage, and navigation; accept only intended `https:` destinations, rejecting credentials, nonstandard ports, and protocols not explicitly required. Centralize validation in `navigateTo` as a final invariant. For real external links, use an ordinary anchor/new browsing context with `rel="noopener noreferrer"` and a documented destination policy. Add tests for `javascript:`, `data:`, `file:`, protocol-relative, encoded/control-character, credential-bearing, mixed-case, and valid HTTPS inputs.
**Regression risk:** Firmware that currently publishes HTTP or non-web schemes will no longer open. If local HTTP development is required, gate it to explicit development builds and loopback hosts rather than production.
**Verification:** Unit-test the final navigation boundary and the trust-persistence path, then connect a fixture advertising each malicious scheme and assert no navigation or script execution. Re-test trusted HTTPS URLs. No browser/device fixture was available in this audit.

### ZMK-SEC-008 — One-byte relay writes reach a two-byte header read

**Severity:** Medium
**Class:** Vulnerability / memory safety
**Evidence:** Audited clone `/tmp/zmk-corne-security-audit/zmk/app/src/split/bluetooth/service.c:100-113` at `4493783ef88ce2e653bf8217c92ee17140df71e3`; the characteristic requires an encrypted write at `/tmp/zmk-corne-security-audit/zmk/app/src/split/bluetooth/service.c:278-282` at the same SHA.
**Impact:** A peer on an encrypted split link can make the peripheral read one byte beyond the supplied GATT attribute value. No disclosure path was established, but the C out-of-bounds read can consume unrelated buffer data and may fault or destabilize firmware depending on the Bluetooth buffer layout.
**Scenario:** Peer sends `WRITE WITHOUT RESPONSE` to the relay-event characteristic with `offset=0` and `len=1`; the initial check rejects only zero length or an oversized aggregate; `memcpy(header, buf, sizeof(struct relay_event_header))` then reads two bytes from the one-byte value before any minimum-header validation.
**Recommendation:** Reject `len < sizeof(struct relay_event_header)` and every nonzero offset before copying the header; retain the existing maximum-field and exact-total-length checks after that guard.
**Regression risk:** Strict rejection removes any accidental fragmented-write behavior. The characteristic already says offset support is absent and uses write-without-response, so a full-frame-only contract should be validated against the actual central.
**Verification:** Add a host-side GATT parser test for lengths 0, 1, exact header, exact valid frame, maximum valid frame, and oversized fields under ASan/UBSan where possible; on hardware, send the same encrypted writes and confirm rejection without reset or event delivery.

### ZMK-SEC-009 — Full Studio RX ring buffer traps BLE callback in an infinite loop

**Severity:** Medium
**Class:** Vulnerability / denial of service
**Evidence:** Audited clone `/tmp/zmk-corne-security-audit/zmk/app/src/studio/gatt_rpc_transport.c:63-85` and default 30-byte RX capacity at `/tmp/zmk-corne-security-audit/zmk/app/src/studio/Kconfig:97-103` at `4493783ef88ce2e653bf8217c92ee17140df71e3`; BLE Studio transport is enabled by default at `/tmp/zmk-corne-security-audit/zmk/app/src/studio/Kconfig:74-80` at the same SHA.
**Impact:** An encrypted BLE Studio client can trap Bluetooth callback processing indefinitely, preventing RPC notification and denying Bluetooth processing until watchdog/reset intervention.
**Scenario:** With `handling_rx=true`, encrypted client sends a Studio GATT write whose length exceeds current free RX-ring capacity; callback copies until the 30-byte default ring fills; `ring_buf_put_claim()` then returns zero, `copied` does not advance, loop never exits, and `zmk_rpc_rx_notify()` is never reached.
**Recommendation:** Before copying, atomically reject a write that exceeds current ring-buffer free space, or implement bounded backpressure that exits callback and resumes only after consumer progress; never wait or spin inside Bluetooth write callback. Define one full-write acceptance contract so rejected data cannot leave a partial RPC frame.
**Regression risk:** Whole-write rejection can require client retry/framing changes and can expose existing assumptions about ATT write size versus RPC ring capacity; asynchronous backpressure adds synchronization and disconnect cleanup complexity.
**Verification:** Host test should prefill RX ring to controlled free capacities, submit writes at `free`, `free+1`, and larger-than-empty-capacity sizes, and assert bounded callback return, no partial enqueue on rejection, and notification only for accepted bytes. Hardware test should negotiate a sufficiently large BLE MTU, send an encrypted oversized or rapid write sequence, and confirm BLE remains responsive, callback returns, malformed RPC is rejected, and later valid RPC succeeds.

### ZMK-SEC-010 — Studio framing buffers an unbounded hostile-device response

**Severity:** Medium
**Class:** Vulnerability / client availability
**Evidence:** The locked ts-client dependency creates a per-decoder `number[]`, appends every in-frame byte, and emits only on EOF; it has no maximum frame length or reset-on-limit path (`/tmp/zmk-corne-security-audit/zmk-studio-ts-client/src/framing.ts:35-79` at `39083858775d320018716e3d8fd68d00f6d11118`). The RPC connection pipes transport bytes through this decoder and then protobuf-decodes the completed allocation (`/tmp/zmk-corne-security-audit/zmk-studio-ts-client/src/index.ts:40-49`). DYA accepts a browser-selected BLE, Web Serial, or WebUSB device (`/tmp/zmk-corne-security-audit/dya-studio/src/components/DeviceConnection.tsx:224-244`); its WebUSB pump continuously enqueues successful bulk packets (`/tmp/zmk-corne-security-audit/dya-studio/src/lib/transport/webUsb.ts:194-237`). Audited source SHA: `2c31a8655dcef95589ce6131a0797ccc19c618b8`.
**Impact:** A selected hostile device can send SOF followed by an arbitrarily long byte stream without EOF, growing browser memory until the tab becomes unresponsive or terminates. Browser device selection/previous grant is required; this is not remote Internet reachability.
**Scenario:** A malicious USB/BLE peer completes connection, starts a response frame, and continuously sends ordinary unescaped bytes. Decoder memory grows even though no valid RPC response is produced.
**Recommendation:** Define a protocol maximum based on the largest legitimate response, reject and reset frames that exceed it, and bound transport/read queues. For legitimately large replies, use explicit chunking with bounded total length. Add hostile-stream tests for no EOF, excessive escaped bytes, repeated SOF, and maximum-size valid frames.
**Regression risk:** A limit below current diagnostic/keymap response size will reject valid devices. Measure maximum encoded responses and leave a documented margin before enforcing it.
**Verification:** Feed the decoder a byte stream above the limit and assert bounded memory, connection teardown, and a recoverable UI error; test maximum legal keymap/diagnostic frames over each transport. No hardware stress test was run.

### ZMK-SEC-011 — RPC timeout rejects the UI call but leaves the global RPC mutex held

**Severity:** Medium
**Class:** Vulnerability / client availability and state-machine integrity
**Evidence:** `call_rpc` serializes every connection through one module-global mutex and waits for `reader.read()` without a per-call abort or timeout (`/tmp/zmk-corne-security-audit/zmk-studio-ts-client/src/index.ts:84-134` at `39083858775d320018716e3d8fd68d00f6d11118`). The React dependency races that promise against an inactivity timeout (`/tmp/zmk-corne-security-audit/react-zmk-studio/src/ZMKCustomSubsystem.ts:50-67`), but its timeout helper only rejects the wrapper and never cancels the underlying RPC/read (`/tmp/zmk-corne-security-audit/react-zmk-studio/src/utils.ts:38-73`), all at `ceda0a4117078af35aed498c9b3afcb85cc68f62`. DYA routes custom calls through that wrapper with a 30-second default (`/tmp/zmk-corne-security-audit/dya-studio/src/hooks/useCustomSubsystem.ts:34-35` and `/tmp/zmk-corne-security-audit/dya-studio/src/hooks/useCustomSubsystem.ts:86-134`). The initial connection handshake correctly recognizes this risk and aborts its stream on timeout (`/tmp/zmk-corne-security-audit/react-zmk-studio/src/useZMKApp.ts:194-220`), but normal post-connect calls do not. Audited source SHA: `2c31a8655dcef95589ce6131a0797ccc19c618b8`.
**Impact:** After a hostile or faulty device withholds one post-connect response, the UI reports a timeout while the hidden call still owns the process-wide mutex. Later official and custom RPCs across the app wait indefinitely until disconnect aborts the connection. This can make later UI actions appear independently broken and may retain closures/readers longer than intended.
**Scenario:** Device answers the handshake, then stays silent for a settings RPC. DYA reports the 30-second timeout; the next keymap, lock-state, or diagnostics call cannot acquire the global mutex.
**Recommendation:** Give each RPC an abort signal/deadline that cancels its pending reader and releases the mutex, or close/replace the connection on timeout. Scope serialization to a connection rather than the module, and ensure late responses cannot satisfy a later request. Keep the existing request-ID correlation check (`/tmp/zmk-corne-security-audit/zmk-studio-ts-client/src/index.ts:103-125`). Audited source SHA: `39083858775d320018716e3d8fd68d00f6d11118`.

**Evidence:** Every local keymap layer supplies two encoder bindings, `&rsr_vol &rsr_trans`, at `config/eyelash_corne.keymap:61`, `config/eyelash_corne.keymap:73`, `config/eyelash_corne.keymap:85`, and `config/eyelash_corne.keymap:97`; the locked build reports eight excess-initializer warnings at `/tmp/zmk-corne-security-audit/build-studio-left-locked.log:287-289`, `/tmp/zmk-corne-security-audit/build-studio-left-locked.log:497-499`, `/tmp/zmk-corne-security-audit/build-studio-left-locked.log:707-709`, `/tmp/zmk-corne-security-audit/build-studio-left-locked.log:917-919`, `/tmp/zmk-corne-security-audit/build-studio-left-locked.log:1261-1263`, `/tmp/zmk-corne-security-audit/build-studio-left-locked.log:1339-1341`, `/tmp/zmk-corne-security-audit/build-studio-left-locked.log:1417-1419`, and `/tmp/zmk-corne-security-audit/build-studio-left-locked.log:1495-1497`. **Impact:** Generated firmware discards each layer's second `rsr_trans` initializer, so physical encoder behavior does not match declared configuration and one intended mapping is unavailable.
**Scenario:** User rotates the single physical encoder on any layer expecting the two declared runtime-sensor bindings to be represented; generated sensor capacity is one, compiler accepts only the first initializer, and `rsr_trans` is dropped. This is reachable input behavior, not a demonstrated security boundary bypass.
**Recommendation:** Define exactly one binding per physical sensor per layer, or change the devicetree/model so declared sensor count and `ZMK_KEYMAP_SENSORS_LEN` agree. Add build-time validation that rejects excess sensor bindings instead of compiling truncated initializers.
**Regression risk:** Selecting one binding changes intended encoder semantics and may remove a runtime-switching workflow; increasing modeled sensor count can change generated keymap layout and runtime-sensor assumptions.
**Verification:** Build every artifact with excess-initializer warnings fatal, inspect generated sensor arrays for exact declared capacity, and physically test clockwise/counter-clockwise encoder behavior on every layer after the user approves a remediation choice.

### ZMK-SEC-021 — Settings-reset handler can index a zero-length keymap

**Severity:** Low
**Class:** Memory-safety hardening gap / recovery artifact
**Evidence:** The settings-reset build reports zero-length keymap array indexing at `/tmp/zmk-corne-security-audit/build-settings-reset.log:250-256`; relevant declarations and accesses are `/tmp/zmk-corne-security-audit/zmk/app/src/keymap.c:64-68`, `/tmp/zmk-corne-security-audit/zmk/app/src/keymap.c:704-713`, and `/tmp/zmk-corne-security-audit/zmk/app/src/keymap.c:716-724` at `4493783ef88ce2e653bf8217c92ee17140df71e3`. **Impact:** If any future, mocked, or alternate path delivers a position event to `zmk_keymap_position_state_changed()` in a zero-keymap recovery build, the handler can access outside the zero-length active-layer array, causing undefined behavior, crash, or memory corruption.
**Scenario:** Current static reset DTS provides no key event, so present reachability is not demonstrated. A test injection, later shield change, or alternate caller supplies position zero; handler indexes `zmk_keymap_active_behavior_layer[position]` even though `ZMK_KEYMAP_LEN` is zero.
**Recommendation:** Compile out or explicitly guard position-event processing when `ZMK_KEYMAP_LEN == 0`, or establish and enforce a contract that makes the handler unreachable in zero-keymap builds. Do not treat a linked settings-reset UF2 as runtime-safe until one gate is proved.
**Regression risk:** Guarding the recovery build can change future reset-shield input behavior; compiling out the handler may reveal callers that implicitly depend on it.
**Verification:** Add a native/instrumented zero-keymap test that injects position zero under ASan/UBSan where possible; prove bounded rejection or compile-time exclusion, rebuild settings-reset warning-free, then run the approved recovery checklist on hardware.
